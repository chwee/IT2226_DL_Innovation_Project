Containerising a RAG chatbot with Docker Model Runner

You will take the OralLink RAG Tester — a FastAPI retrieval-augmented chatbot that already runs on your machine — and stand it up as a two-container Docker stack that talks to a large language model running locally through Docker Model Runner. No cloud, no API key, no data leaving your laptop.

Bench check

10 min

Confirm the four things this lab depends on before you spend fifteen minutes downloading a model onto a machine that cannot run it.

Open Windows PowerShell (not the old Command Prompt) and move into the project folder. Every command in this lab is run from this folder unless the terminal header says otherwise.

PowerShell — repo root
PS> cd C:\MyWork\_NYP_Project\Orallink\TestDockerModelRunner
PS> dir

You should see Dockerfile, docker-compose.yml, nginx\, backend\ and query_model.py. If you do not, you are in the wrong folder — everything after this will fail in confusing ways.

1 · Docker Desktop is running

PowerShell
PS> docker version

Both a Client and a Server block must appear. A client-only reply with error during connect means the Docker Desktop engine is not started — launch Docker Desktop from the Start menu and wait for the whale icon to stop animating.

2 · Model Runner is enabled

Docker Model Runner is a Docker Desktop feature that runs GGUF language models on your own hardware and exposes them behind an OpenAI-compatible HTTP API. It is off by default.

  • Docker Desktop → Settings → AI → tick Enable Docker Model Runner.
  • Tick Enable host-side TCP support and leave the port at 12434. Apply & restart.
PowerShell
PS> docker model status

It should report that the runner is running. If docker model is not a recognised command at all, your Docker Desktop predates Model Runner — update it before continuing.

3 · Port 80 is free

The stack publishes its front door on port 80. IIS, Skype, another nginx or a stray container can already hold it.

PowerShell
PS> netstat -ano | findstr :80

Lines ending LISTENING with local address 0.0.0.0:80 mean something already owns it. Note the fix now — you will need it in Step 3: change the nginx port mapping in docker-compose.yml from "80:80" to "8080:80" and use http://localhost:8080 throughout.

4 · Disk space

The model alone is about 4.8 GB, plus roughly 1 GB for the Python image layers. Have 8 GB free and at least 8 GB of RAM available to Docker Desktop.

Checkpoint

docker version shows a Server block · docker model status reports running · port 80 is free (or you have written down your alternative port).

1

Meet the model on its own, before any app

15 min

Pull a model into Docker Model Runner and talk to it directly, so that you know what the model knows before retrieval is added. This is the baseline the rest of the lab is measured against.

Pull the model

PowerShell — repo root
PS> docker model pull ai/ministral3:8B-Q4_K_M

This downloads roughly 4.8 GB and takes several minutes on campus wifi. While it runs, read ahead to Step 2.

Q4_K_M in the tag is the quantisation level: the model's weights have been compressed from 16-bit floats down to about 4 bits each. That is what makes an 8-billion-parameter model fit in memory on a laptop with no GPU. The trade is a small loss of answer quality for a very large gain in size and speed.

Confirm the exact tag

PowerShell
PS> docker model list
Expected output (shape, not exact figures) 
MODEL NAME                             PARAMETERS  QUANTIZATION  SIZE
docker.io/ai/ministral3:8B-Q4_K_M      8B          IQ2_XXS/Q4_K_M  4.80 GB
Read the tag carefully

You pulled ai/ministral3:8B-Q4_K_M but the list shows docker.io/ai/ministral3:8B-Q4_K_M. The app must be configured with the name as listed here. A tag mismatch is the single most common cause of "model not found" later in this lab.

Call the API by hand

Model Runner listens on http://localhost:12434 and speaks the OpenAI API dialect, so the same request shape you would send to a cloud provider works unchanged.

PowerShell
PS> curl.exe http://localhost:12434/engines/v1/models
PowerShell gotcha

In PowerShell, curl is an alias for Invoke-WebRequest, which takes different flags and prints a different object. Always type curl.exe in this lab so you get the real curl binary.

Ask the raw model an OralLink question

query_model.py is a standalone console client using only the Python standard library — no virtual environment, no dependencies, and no retrieval. It goes straight to the model.

PowerShell — repo root
PS> python query_model.py "What is Oral Link's AI dental screening service?"

The first call may hang for a minute or two while the model is loaded into RAM; after that, responses stream back quickly.

Write down what it says. The model has never seen OralLink's documentation. It will either admit ignorance or — more instructively — invent a plausible-sounding dental company. That invention is the problem retrieval-augmented generation exists to solve, and you will re-ask this exact question in Step 4.

Checkpoint

docker model list shows the Ministral tag · the raw model answered a question · you have noted its (probably wrong) answer about OralLink.

2

Read the blueprint before you build

10 min

Understand what the three configuration files describe, so that Step 3 is a confirmation rather than a magic trick.

The stack is two containers plus one process that is not a container. Trace the path of a single question through this diagram before you run anything.

docker-compose.yml — the stack definition

Open it. Four things are worth naming out loud:

  • build: . under app — this service is compiled from the Dockerfile, not downloaded.
  • expose: "8000" versus nginx's ports: "80:80" — expose opens a port to sibling containers only; ports punches a hole through to Windows. This is why you will browse to http://localhost and not http://localhost:8000.
  • environment: — the model tag, the endpoint, RAG_TOP_K=4 and the token budget are all injected here, not baked into the code.
  • volumes: — backend/data/sample and backend/static are mounted read-only into the running container. Step 5 exploits this.

Why the endpoint address changes inside a container

The .env.example file points at http://localhost:12434, but docker-compose.yml uses a different address for the same service. That is not an inconsistency — it is the single most important networking idea in this lab.

nginx/default.conf — two lines that matter

  • proxy_buffering off; — the app streams answers token by token using Server-Sent Events. With buffering on, nginx would hold the whole response and forward it in one lump; the UI would show a long silence, then a wall of text. The streaming would not error, it would just silently stop feeling live.
  • proxy_read_timeout 910s; — a cold model can take minutes to load on first use. The default 60-second timeout would cut the very first question off.
Checkpoint

You can point at the line in docker-compose.yml that decides which model is used, and explain in one sentence why the app cannot say localhost:12434.

3

Build the image and start the stack

15 min

Turn the source folder into a running image, and see the difference between what is baked in and what is mounted live.

PowerShell — repo root
PS> docker compose up --build -d
  • --build compiles the app image from the Dockerfile first. The first build takes 2–4 minutes because pip has to download FastAPI, uvicorn and httpx; later builds hit the layer cache and take seconds.
  • -d is detached — the containers keep running in the background and you get your prompt back. Drop it to watch logs in the foreground instead, where Ctrl+C stops the stack.

Confirm both containers are up

PowerShell
PS> docker compose ps
Expected output 
NAME                            SERVICE   STATUS    PORTS
testdockermodelrunner-app-1     app       running   8000/tcp
testdockermodelrunner-nginx-1   nginx     running   0.0.0.0:80->80/tcp

Compose names containers <folder>-<service>-1, which is where testdockermodelrunner- comes from. Note the asymmetry in the PORTS column: nginx has a 0.0.0.0:80->80 mapping, the app has only 8000/tcp — exactly what Figure 1 showed.

Watch the app start

PowerShell
PS> docker compose logs -f app
Expected output (tail) 
app-1  | INFO:     Started server process [1]
app-1  | INFO:     Waiting for application startup.
app-1  | INFO:     Application startup complete.
app-1  | INFO:     Uvicorn running on http://0.0.0.0:8000

Ctrl+C stops following the logs. It does not stop the containers — docker compose ps will confirm they are still running.

Checkpoint

Two containers running · nginx mapped to 0.0.0.0:80 · the app log ends with Uvicorn running on http://0.0.0.0:8000.

4

Ask the chatbot, and inspect its evidence

10 min

See retrieval change the model's behaviour on the exact question you asked in Step 1, and read the sources it used.

Open http://localhost in a browser. Not :8000 — nothing is listening there on Windows.

Re-ask the Step 1 question

Type the same question you asked the raw model:

Ask 
What is Oral Link's AI dental screening service?

Compare the two answers side by side. The grounded answer should name the actual service and carry [1]-style citation markers back to the sources panel.

Three more questions, chosen to probe different behaviours

Ask thisWhat to watch for
How much does a dental consultation cost with CHAS?Retrieval should pull from dental_cost_subsidies_enhanced.txt. Check the source panel — the file name and similarity score are shown per chunk.
What does a HIGH overall risk score mean in my screening report?Comes from a different file entirely. Retrieval, not the model, decided that.
Who won the 2018 FIFA World Cup?Nothing in the knowledge base matches. The system prompt instructs the model to say it does not know and to point the user to OralLink rather than guess. This is the behaviour that makes RAG safe to put in front of patients.

Inspect the same thing over the API

PowerShell
PS> curl.exe http://localhost/api/config
PS> curl.exe http://localhost/api/sources

/api/config reports the active model, the endpoint the container is using, the data directory and the number of chunks indexed. Confirm the endpoint really is model-runner.docker.internal and not localhost — that is Figure 2 proving itself at runtime.

Checkpoint

The grounded answer differs from Step 1's · the sources panel names real files with scores · the out-of-scope question is refused rather than invented.

5

Change it while it runs

15 min

Learn which kind of change needs which command — the practical difference between a rebuild, a recreate, and a reload.

A · Add knowledge — no rebuild

Open backend\data\sample\orallink_clinic_info.txt in your editor and paste this block at the end of the file. It follows the same chunk format the retriever parses.

backend\data\sample\orallink_clinic_info.txt — append
--- CHUNK 900 ---
[CHUNK ID]   orallink-nyp-lab-hours
[TOPIC]      OralLink NYP campus screening booth — opening hours
[KEYWORDS]   nyp booth, campus screening, opening hours, walk in
[TRIGGERS]
  - When is the NYP screening booth open?
  - Can I walk in at NYP?
CONTENT:
The OralLink campus screening booth at Nanyang Polytechnic operates on
Tuesdays and Thursdays, 10am to 4pm, at Block L Level 1. Walk-ins are
accepted; a screening takes about 8 minutes and results are emailed
within one working day.
--- END CHUNK 900 ---

Now re-index without restarting anything — click Reload knowledge base in the UI sidebar, or call the endpoint directly:

PowerShell
PS> curl.exe -X POST http://localhost/api/reload

Ask: "When is the NYP screening booth open?" The answer should quote your new chunk. Nothing was rebuilt, nothing restarted — the folder was bind-mounted, so the container saw your edit the moment you saved it.

B · Change a setting — recreate, don't rebuild

In docker-compose.yml, change RAG_TOP_K=4 to RAG_TOP_K=1, then:

PowerShell — repo root
PS> docker compose up -d

Compose notices the environment block changed and recreates the app container from the existing image — no --build. Ask a broad question such as "What should I do about bleeding gums?" and watch the sources panel shrink to one chunk. Answers get thinner. Set it back to 4 and recreate again.

Why editing backend\.env does nothing here

.env is copied into the image, but docker-compose.yml sets the same variable names in the environment before Python starts, and load_dotenv() never overwrites a variable that already exists. .env only takes effect when you run uvicorn directly on the host. Students lose a lot of time to this — edit the compose file, not .env.

C · Swap the model — neither

The sidebar's Active model dropdown lists what Model Runner already has pulled and switches the app at runtime via POST /api/model. It will not pull anything for you: to offer a new model, run docker model pull <tag> first, then reload the page.

The rule, in one table

You changed…CommandWhy
backend/data/sample/*.txtUI reload button, or POST /api/reloadBind-mounted; only the index is stale
backend/static/index.htmlRefresh the browserBind-mounted; served as a static file
An environment: valuedocker compose up -dRecreates the container from the same image
backend/app.py, rag.py, requirements.txtdocker compose up --build -dCopied in at build time; the image is stale
nginx/default.confdocker compose restart nginxMounted config; nginx re-reads it on start
Checkpoint

The chatbot answers a question using text you wrote yourself · you have seen RAG_TOP_K visibly change the sources panel · you can state which of the five changes above needs --build.

6

When it breaks

10 min

Match a symptom to the layer that caused it. Work through any failures you hit; if you hit none, read the table and try inducing the first one deliberately.

Your first move for anything is always the same pair:

PowerShell — repo root
PS> docker compose ps
PS> docker compose logs --tail 50 app nginx
SymptomLayer at faultFix
bind: address already in use on startup Windows host Something already owns port 80. Change nginx's mapping to "8080:80" and browse to http://localhost:8080.
502 Bad Gateway in the browser app container nginx is fine; the app behind it died or never started. docker compose logs app — usually a Python traceback.
Answer never arrives; first question only Model Runner Normal on a cold model — loading 4.8 GB into RAM takes minutes. The proxy allows ~15 minutes. Wait once; later questions are fast.
model not found / 404 from the model call Config DMR_MODEL does not match a pulled tag. Run docker model list and copy the name exactly, including the docker.io/ prefix.
Connection refused or DNS failure to the model Networking Model Runner disabled, or DMR_BASE_URL still says localhost. Re-read Figure 2, check Docker Desktop → Settings → AI.
Answers arrive all at once, not token by token nginx proxy_buffering off; is missing or was edited out. Restore it, then docker compose restart nginx.
A question in Chinese or Tamil retrieves nothing Retriever (by design) Not a bug in your setup. rag.py tokenises Latin script only and the knowledge base is English. Genuine multilingual RAG needs a Unicode-aware tokeniser and translated documents — out of scope here.
Empty answer, but the reasoning block was full Model choice Only affects reasoning models such as gpt-oss or SEA-LION: the chain-of-thought consumed the whole RAG_MAX_TOKENS budget. Raise it or lower REASONING_EFFORT. Ministral never does this — it is not a reasoning model.
Diagnostic habit worth keeping

Work the layers in order: is the container running (ps) → did the app start (logs app) → can the app reach the model (/api/config, then docker model list). Guessing at the top of the stack when the bottom is broken wastes the most time.

7

Tear down cleanly

5 min

Return the machine to the state you found it in — lab PCs are shared.

PowerShell — repo root
PS> docker compose down
PS> docker compose ps          # should list nothing

down stops and removes both containers and the network Compose created. It leaves the built image on disk, so your next docker compose up -d starts in seconds.

The model stays loaded in Model Runner independently of the containers. Leave it if the next class needs it; remove it if the lab PC is short of disk:

PowerShell
PS> docker model list
PS> docker model rm docker.io/ai/ministral3:8B-Q4_K_M   # optional
PS> docker system df                                     # what Docker is holding
Undo your edits

If you added CHUNK 900 in Step 5, remove it (or restore the file from git) before you leave, so the next group starts from the same knowledge base you did.

A

Where this goes in production

read only

Not run in this session. Read it to see how little of what you just built actually changes when it ships to a GPU server.

The production path ships the image, not the source. The server never gets a copy of the repository, never installs Python, and never runs a Docker build — which is exactly why the container abstraction is worth the effort.

The rest of the production story, documented in the project's own README.md: an NVIDIA driver plus the NVIDIA Container Toolkit on the instance, the Model Runner plugin installed on Docker Engine (Desktop is not available on a server), and a larger model — GPT-OSS-20B or Qwen SEA-LION v4 32B — that is only comfortable with a GPU behind it. SEA-LION measured about 0.34 tokens/second on CPU-only Docker Desktop: technically working, practically unusable.

Intentionally out of scope for this lab

  • TLS/HTTPS — the stack is plain HTTP on port 80, locally and on EC2. Real exposure needs certbot in front of nginx, or TLS terminated at an ALB.
  • A real vector store — rag.py is pure-Python TF-IDF with no embeddings. It demonstrates the pattern; it is not a production retriever.
  • Authentication, rate limiting, log persistence — none are present.
  • Multi-container orchestration beyond Compose — no Kubernetes, no swarm, no autoscaling.
  • Model fine-tuning or evaluation — the model is used as pulled.

Self-check — can you explain each of these without looking?

  • Why the app container's address for the model is model-runner.docker.internal and not localhost.
  • The difference between expose and ports, and why you browse to port 80 rather than 8000.
  • Which file edits need --build, which need up -d, and which need neither.
  • What proxy_buffering off is protecting, and what the symptom would be without it.
  • Why the same question produced a different answer in Step 1 and Step 4 — with no change to the model.
  • What RAG_TOP_K controls, and what you observed when you set it to 1.
  • Why the chatbot refused the World Cup question, and where that behaviour is defined.

Facilitator notes

Not part of the learner walkthrough

Pre-lab preparation

  • Pull the model onto lab PCs beforehand. Thirty simultaneous 4.8 GB downloads will consume the session. If the images cannot be pre-staged, run Step 1's pull as a whole-class action at the very start and cover Step 2's theory while it downloads.
  • Verify Docker Desktop on the lab image is recent enough to have Model Runner under Settings → AI, with host-side TCP available.
  • Check port 80 on the standard lab image. If it is taken estate-wide, edit docker-compose.yml to "8080:80" in the distributed copy and tell students to substitute the URL throughout.
  • Confirm Docker Desktop is allocated at least 8 GB of RAM in the WSL2 backend settings.

Timing at 90 minutes

Steps 0–4 are the core (50 minutes) and every student should complete them. Step 5 is where understanding consolidates; protect at least 15 minutes for it even if it means compressing Step 6 into a demonstration. The appendix is reading, not doing — assign it as pre-reading for the next session if time runs short.

Discussion prompts

  • After Step 1 vs Step 4: the model did not learn anything between those two answers — so what actually changed? Draws out the distinction between retrieval and training.
  • After Step 5B: what would go wrong with RAG_TOP_K=20? Leads to context windows, latency and cost.
  • After the World Cup question: is refusing to answer a failure or a feature? Connects to responsible AI and clinical liability.

Known rough edges

  • First model call after a Docker Desktop restart is slow enough that students will assume it has hung. Warn them before Step 4, not during.
  • PowerShell's curl alias trips at least one student per class; the lab uses curl.exe everywhere for this reason.
  • Students who edit backend\.env instead of docker-compose.yml will see no effect and no error. The callout in Step 5B addresses it, but it is worth saying aloud.
