# Design Thinking Workshop

### From Initial Scenario → Validated Problem Statement / Solution

**Format:** 1-day intensive (can be split into 5 half-day sessions across a week)
**Group size:** 4–6 people per team, 3–6 teams
**Facilitator role:** Timekeeper, prompts teams to produce the *required deliverable* before moving on — no team advances to the next phase without it.

## How the Workshop Chains Together

Each phase produces one **mandatory artifact**. That artifact is the *only* input the next phase's team is allowed to start from — this forces rigor and stops teams from jumping straight to solutions.

```
Scenario/Prompt
   │
   ▼
[1] EMPATHIZE ──► Empathy Map + User Quotes/Data
   │
   ▼
[2] DEFINE ──► Point-of-View (POV) Problem Statement + "How Might We" (HMW) list
   │
   ▼
[3] IDEATE ──► Ranked Concept Shortlist (2–3 ideas) + Rationale
   │
   ▼
[4] PROTOTYPE ──► Low-Fidelity Prototype + Test Script
   │
   ▼
[5] TEST ──► Validated (or Pivoted) Solution Statement + Evidence Log
   │
   ▼
Final Deliverable: Solution Brief
```

---



## Pre-Workshop: The Scenario Brief (Input)

Before Phase 1 starts, give every team the same **starting scenario** — e.g., a messy, real situation, not a problem statement (a problem statement is what they'll *earn* in Phase 2).

**Example scenario prompt:**

> "Students at a polytechnic frequently miss submission deadlines for practical assignments, even when deadlines are posted on the LMS well in advance."

**Deliverable checklist for the brief:**

- [ ] 2–4 sentence scenario description (situation, not a solution)
- [ ] Named stakeholder group(s) to investigate
- [ ] Any constraints (time, budget, tech, policy)
- [ ] What "success" will be judged against at the end of the day

---



## Phase 1 — EMPATHIZE (60–90 min)

**Goal:** Understand the people inside the scenario before touching the problem.

**Activities:**

1. Review any provided data (survey results, interview clips, support tickets) or run 3–5 quick mock/real interviews.
2. Each member fills an **Empathy Map** for one user type: Says / Thinks / Does / Feels.
3. Cluster raw notes on a wall/board — look for contradictions (what people *say* vs. what they *do*) — these are gold.

**Facilitator prompts:**

- "What surprised you?"
- "Where did the user's words and actions disagree?"



### ✅ Required Deliverable → passed to Phase 2

**Empathy Synthesis Sheet**, containing:

- 1 completed Empathy Map per user type
- 3–5 direct verbatim quotes
- 3+ observed behaviors/pain points (not assumptions)
- 1–2 "aha" contradictions or tensions

*Gate rule: A team cannot proceed to Define without at least one direct quote and one behavioral observation — assumptions alone are rejected.*

---



## Phase 2 — DEFINE (45–60 min)

**Goal:** Convert empathy data into one sharp, actionable problem statement.

**Activities:**

1. From the Empathy Synthesis Sheet, extract **Needs** (verbs, not nouns — e.g., "needs a way to feel less overwhelmed," not "needs an app").
2. Write insight statements: *"[User] needs a way to [need] because [surprising insight]."*
3. Draft a **POV (Point of View) statement**:
  `[Specific user] needs [need] because [insight].`
4. Reframe into 3–5 **"How Might We" (HMW)** questions — broad enough to allow many solutions, narrow enough to be actionable.
5. Vote/dot-select the single strongest HMW to carry forward.



### ✅ Required Deliverable → passed to Phase 3

**Problem Statement Card**, containing:

- Final POV statement
- Top 1 (max 2) HMW question(s)
- The insight/evidence line from Phase 1 that justifies it (traceability back to empathy data)

*Gate rule: Teams cannot bring more than 2 HMWs into Ideation — forces focus.*

---



## Phase 3 — IDEATE (45–75 min)

**Goal:** Generate volume, then converge to a shortlist.

**Activities:**

1. **Diverge:** Brainstorm against the chosen HMW using a technique such as Crazy 8s (8 ideas in 8 minutes) or round-robin brainwriting. Rule: no criticism during generation.
2. **Cluster** similar ideas; discard true duplicates.
3. **Converge:** Use a 2x2 matrix (e.g., Impact vs. Feasibility) or dot-voting to shortlist top 2–3 concepts.
4. For each shortlisted concept, write one sentence: *what it is, who it helps, why it addresses the POV.*



### ✅ Required Deliverable → passed to Phase 4

**Ranked Concept Shortlist**, containing:

- Top 2–3 concepts, each with a one-line description
- Impact/Feasibility placement or vote count justifying the ranking
- The single concept selected to prototype, and why it beats the runner-up

*Gate rule: The selected concept must explicitly reference the POV/HMW — no orphan ideas.*

---



## Phase 4 — PROTOTYPE (60–90 min)

**Goal:** Make the top idea tangible enough to react to — not to be pretty.

**Activities:**

1. Choose the *lowest-fidelity* format that still tests the core assumption: paper sketch, storyboard, clickable wireframe, role-play script, or physical mock-up.
2. Build only the parts of the experience needed to test the riskiest assumption (the part most likely to be wrong).
3. Write a short **Test Script**: what you'll show, what question you're trying to answer, what a "pass" vs "fail" reaction looks like.



### ✅ Required Deliverable → passed to Phase 5

**Prototype Package**, containing:

- The physical/digital prototype (photo, sketch, or link)
- 1 named "riskiest assumption" being tested
- A 3–5 question Test Script with explicit success/fail criteria written *before* testing (to prevent post-hoc rationalizing)

*Gate rule: If the team can't name the riskiest assumption, they must return to Ideate — a prototype without a hypothesis is just a craft project.*

---



## Phase 5 — TEST (45–60 min)

**Goal:** Get real reactions and decide: validate, pivot, or discard.

**Activities:**

1. Run the prototype past 3–5 real or proxy users (can be another team acting as users, if time-boxed).
2. Observe more than you explain — resist defending the idea.
3. Log reactions against the pre-written success/fail criteria.
4. Decide as a team: **Validated** (evidence supports it) / **Pivot** (partial signal, needs a tweak) / **Discard & return to Define** (evidence contradicts the POV).



### ✅ Final Deliverable

**Solution Brief (1 page)**, containing:

1. Original scenario
2. Final POV / problem statement (traced back to empathy evidence)
3. Chosen solution concept
4. What was tested and the actual user evidence (quotes/observations, not opinions)
5. Verdict: Validated / Pivoted / Discarded — with reasoning
6. Recommended next step (e.g., build MVP, test v2, or re-enter Empathize with a new question)

## Assessment / Debrief Rubric (optional, for a classroom setting)


| Criterion             | What "good" looks like                                                                                   |
| --------------------- | -------------------------------------------------------------------------------------------------------- |
| Traceability          | Final solution can be traced back through every deliverable to the original scenario                     |
| Evidence over opinion | Claims are backed by quotes/observations, not "we think users want..."                                   |
| Focus                 | Only one POV/HMW carried through past Define                                                             |
| Honest testing        | Fail criteria were set *before* testing, and pivots/discards are treated as valid outcomes, not failures |

### Notes on adapting this for your NYP context

- Works well as a module capstone: give each team a different scenario drawn from real IT/industry pain points (e.g., onboarding, data quality, deployment friction) so outputs double as portfolio evidence.
- Each phase's gate rule doubles as a natural assessment checkpoint — you could grade the 5 deliverables individually rather than only the final brief.
- If you want this compressed into 3 hours, merge Ideate+Prototype and cut Test down to a "would this work?" structured peer critique instead of live user testing.
